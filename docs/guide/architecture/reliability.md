# Надёжность и резервные копии

## Механизмы восстановления

| Компонент | Поведение при отказе |
|---|---|
| API / worker | `restart: unless-stopped`, healthcheck, переподключения. Сам статус `unhealthy` не перезапускает процесс. |
| Redis | Без дисковой персистентности; API читает PostgreSQL при недоступности кеша. |
| PostgreSQL | Persistent volumes и асинхронный standby; promotion выполняет оператор. |
| RabbitMQ | Три узла, quorum 2/3, автоматический выбор лидера и переподключение клиентов. |
| Outbox | Изменения БД сохраняются при отказе брокера; доставка возобновляется после восстановления. |

Readiness API требует PostgreSQL/outbox, но не Redis/RabbitMQ. Холодный запуск
Compose ждёт healthy-зависимостей; работа уже запущенного API допускает
деградацию кеша и брокера.

## Авария PostgreSQL primary

```bash
CHECKERS_DISRUPTIVE=1 python3 -B tests/integration/test_postgres_failover.py -v
```

Сценарий: создать партию и ход → дождаться WAL на standby → SIGKILL primary
с отключённым restart → запрет запуска старого узла → promotion → чтение
и новый ход на новом primary → rejoin старого узла и проверка репликации.

Команды обслуживания находятся в `infra/postgres/`: `postgres-primary.sh`
определяет writable-узел; `promote-postgres.sh` повышает standby при остановленном
старом primary, обновляет `.env`, пересоздаёт API и очищает `game:*` в Redis;
`rejoin-postgres.sh` архивирует старый PGDATA и выполняет `pg_rewind`.
После прерывания сначала проверяют роли: старый primary нельзя запускать
вслепую. Имена контейнеров не определяют их текущие роли.

Репликация асинхронная: последние непереданные транзакции могут потеряться.
Тест ждёт репликации контрольного хода и потому не доказывает RPO=0.
Переключение ручное и сопровождается простоем API.

## Авария RabbitMQ

```bash
CHECKERS_DISRUPTIVE=1 python3 -B tests/integration/test_rabbitmq_failover.py -v
```

Первый сценарий останавливает worker, подтверждает событие в очереди,
аварийно завершает её лидера и проверяет выбор нового. При выключенном старом
лидере должны обработаться и backlog, и новое событие. Второй сценарий
отключает фактический узел подключения worker: API и worker должны
переподключиться без перезапуска. После возврата узлов проверяется догоняние реплик.

При потере двух узлов quorum отсутствует: новые события остаются в outbox.
Авторестарт процессов, отказ Redis/БД, потеря quorum и полный отказ брокера
проверяются отдельно:

```bash
CHECKERS_DISRUPTIVE=1 python3 -B tests/integration/test_failure.py -v
```

## Параметры обслуживания

**MTBF** — суммарное время штатной работы / число незапланированных отказов.
Цель каждого компонента — ≥8 ч, один рабочий день. Искусственные
отказы не учитываются; длительных наблюдений нет, фактический MTBF неизвестен.

**MTTR** — среднее время восстановления. В тесте авторестарта измеряется
время от команды завершения процесса до `healthy` и роста `RestartCount`.
Отдельный опыт проверяет цель восстановления, но не измеряет среднее.

**SLI** — измеряемый показатель, **SLO** — его целевое значение:

| Показатель | Цель и основание |
|---|---|
| Авторестарт API / worker / Redis | ≤30 с; запас на таймауты и healthcheck. |
| Авторестарт PostgreSQL / RabbitMQ | ≤60 с; дополнительное время на восстановление хранилища/соединений. |
| Переключение PostgreSQL | ≤60 с от аварии до новой записи, без ожидания реакции оператора и rejoin. |
| Отказ лидера/узла RabbitMQ | ≤60 с до обработки события при оставшихся 2/3 узлах. |
| Корректное чтение | ≥99 из 100 запросов; проверяется содержимое, не только HTTP 200. |
| p95 корректных чтений | ≤0,5 с; приемлемая задержка интерактивной игры. Время curl внутри API, без Docker exec. |
| Доставка `game.created` | 5/5 событий за ≤15 с от начала создания; запас на повторы. |
| Backup + restore | ≤300 с для небольшой БД. |

Это локальные приёмочные цели, не месячная доступность и не нагрузочный тест.
Автоматически проверяются корректность, задержка и доставка событий,
ресурсы можно смотреть через `docker stats`. Prometheus/Grafana не развёрнуты.

## Backup и restore

`infra/backups/backup.sh` выполняет `pg_dump -Fc` текущего primary, проверяет
архив через `pg_restore --list` и сохраняет его в `backups/` вне тома БД.
Каталог имеет права 700, архив — 600. После успешного dump удаляются архивы
старше 7 дней. `BACKUP_DIR` и `BACKUP_RETENTION_DAYS` меняют эти значения.

`backup-timer.sh install` из того же каталога устанавливает ежедневный запуск
в 02:00 в пользовательском systemd. Нужен работающий user manager;
`Persistent=true` догоняет пропущенный запуск. `restore.sh` создаёт только
новую проверочную БД и отказывается перезаписывать существующую.

```bash
python3 -B tests/integration/test_backup.py -v
```

Тест сравнивает восстановленную партию, двух игроков и ход, проверяет права,
ротацию и запрет перезаписи; затем удаляет свою временную БД и архивы.
Ручные команды — на [главной странице](../index.md).

Реплика не заменяет backup: ошибочное удаление тоже реплицируется. Все узлы
и бэкапы находятся на одном хосте; потеря хоста/диска остаётся общей точкой
отказа. PITR и удалённого backup нет. Архивы PGDATA перед rejoin хранятся
отдельно и автоматически не ротируются.

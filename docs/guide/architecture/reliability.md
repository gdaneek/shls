# Надёжность и отказы

## API, Redis и outbox

Процессы используют restart policy и healthcheck. `live` показывает, отвечает
ли API; `ready` проверяет PostgreSQL и outbox, но не требует доступности Redis
или RabbitMQ. Сам `unhealthy` не означает автоматического перезапуска процесса.

Redis — восстанавливаемый кеш. При его отказе чтение может идти из PostgreSQL.
При недоступности брокера API может сохранить изменение и outbox-событие;
публикация возобновится после восстановления связи. Дубли событий возможны.
Эти взаимодействия описаны в [потоках](flows.md).

## PostgreSQL primary / standby

У `postgres` и `postgres-standby` отдельные тома, роли могут меняться.
Репликация WAL асинхронная. Если primary аварийно завершился, оператор
останавливает и ограждает старый узел, повышает standby, перенаправляет API
и затем возвращает старый узел через архивирование PGDATA и `pg_rewind`.
Переключение API включает его пересоздание, не является автоматическим HA и
может сопровождаться простоем.

При аварии последние транзакции, ещё не дошедшие до standby, могут потеряться.
Нельзя обещать RPO=0. Перед rewind создаётся физический архив старого PGDATA;
он не заменяет регулярный логический backup и отдельно не ротируется автоматически.

## RabbitMQ quorum

Очередь `game.events.quorum` имеет три voting replicas. Для работы необходимо
большинство 2/3; при отказе лидера оставшиеся узлы выбирают нового. Клиенты
при разрыве перебирают адреса. При потере большинства очередь не подтверждает
новые сообщения, и outbox продолжает хранить ожидающие события.

Publisher confirm и ACK после обработки защищают описанный путь от ряда
отказов, но повторная доставка возможна. Worker логирует событие, а
бизнес-дедупликация не реализована. Этот механизм не делает PostgreSQL
синхронным и не устраняет потерю всего хоста.

## Бэкапы и общие пределы

`infra/backups/backup.sh` создаёт логический dump текущего writable-узла в
`backups/`, вне его основного тома. `infra/backups/restore.sh` восстанавливает
его в новую тестовую БД, не поверх рабочей; после успешного восстановления
эта БД остаётся для проверки. Автоматический `test_backup.py` удаляет свою
временную БД и архивы после проверки.

`infra/backups/backup-timer.sh install` устанавливает пользовательский systemd
timer на 02:00 по локальному времени. Он работает при запущенном user manager;
`Persistent=true` позволяет выполнить пропущенный запуск при его возвращении.
После успешного dump удаляются логические архивы старше 7 дней. Физические
архивы перед rejoin в эту ротацию не входят.
Реплика не заменяет резервную копию, поскольку ошибочное удаление тоже
реплицируется.

Все реплики и бэкапы по умолчанию находятся на одной машине. Потеря хоста
или общего диска остаётся общей точкой отказа; удалённого бэкапа, PITR и
гарантированной нулевой недоступности в этом стенде нет.

Цели и способы измерения — в [параметрах надёжности](service-levels.md).

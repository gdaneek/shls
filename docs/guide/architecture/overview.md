# Контейнеры системы — C2

## Компоненты и связи

```{graphviz} ../_static/system.dot
:alt: Игрок через frontend обращается к Game API, PostgreSQL, Redis и RabbitMQ; Event Worker получает события
```

Исходник схемы — `docs/guide/_static/system.dot`. Sphinx с Graphviz строит
SVG внутри `build/docs/html/`.

| Компонент | Ответственность | Чего он не делает |
|---|---|---|
| `frontend` | Отдаёт страницу, направляет `/api/` в API. | Не решает правила и не хранит серверные секреты. |
| `game-api` | Создаёт/читает игры, проверяет токены и ходы, сохраняет изменения. | Не полагается на память процесса как на хранилище партии. |
| PostgreSQL | Хранит авторитетные данные партий и outbox. | Standby сам не становится primary без оператора. |
| Redis | Ускоряет чтения кешированного состояния. | Не является источником истины. |
| RabbitMQ | Хранит и реплицирует очередь игровых событий. | Не хранит состояние игровой доски. |
| `event-worker` | Получает события, пишет JSON в stdout, подтверждает обработку. | Не подключается к PostgreSQL или Redis. |

В обычном Compose-стеке девять контейнеров: frontend, API, worker, два узла
PostgreSQL, Redis и три узла RabbitMQ. Временный `postgres-maintenance` из
профиля `tools` запускается только при обслуживании и не является ещё одним
бизнес-сервисом.

## Владение и взаимодействие

Game API — владелец игровых таблиц. При изменении партии PostgreSQL одной
атомарной SQL-командой фиксирует состояние и запись события в outbox. После
коммита API сбрасывает ключ Redis. Отдельный поток API позже отправляет
событие в RabbitMQ; Event Worker читает его из очереди и логирует.

При чтении API сначала проверяет Redis и при промахе получает состояние из
PostgreSQL. События — асинхронное уведомление, не способ изменить доску
в обход API. Изложение потоков — в статьях [запись и обработчики](backend.md),
[кеш](cache.md) и [события](events.md).

## Роли узлов

Узлы `postgres` и `postgres-standby` имеют постоянные имена и отдельные тома,
но **не постоянные роли**: после управляемого переключения любой из них может
оказаться primary. API подключается к одному выбранному primary. Три узла
RabbitMQ образуют кластер, а лидер quorum-очереди выбирается автоматически;
клиент подключается к одному из узлов и переподключается при отказе.

Все узлы находятся на одном хосте и, как правило, одном диске. Это позволяет
демонстрировать отказ отдельного контейнера, но не переживает потерю всей
машины. Подробнее — [надёжность](reliability.md).

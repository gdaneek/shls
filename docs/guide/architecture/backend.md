Схема показывает компоненты одного процесса Game API; PostgreSQL, Redis и
RabbitMQ находятся за его пределами.

## Исходники и запуск

| Файл | Назначение |
|---|---|
| `src/game-api/main.cc` | Настройка клиентов, загрузка схемы, health и запуск Drogon. |
| `src/game-api/game_api.cc`, `shls/game_api.h` | Регистрация HTTP-маршрутов, работа с SQL/Redis, ответы. |
| `src/game-api/game_rules.cc`, `shls/game_rules.h` | Игровая логика без HTTP и хранилищ. |
| `src/game-api/event_publisher.cc`, `shls/event_publisher.h` | Фоновая публикация записей outbox. |
| `infra/postgres/schema.sql` | Каноническая схема и совместимые изменения. |

При старте API создаёт клиентов PostgreSQL и Redis, применяет SQL-схему,
запускает поток publisher, регистрирует маршруты и слушает внутренний порт
8000. Если первичное применение схемы получает исключение БД, выполняются
повторы; отсутствие или пустота SQL-файла является ошибкой старта.

Drogon настроен на два HTTP-потока. Запросы к PostgreSQL и Redis в HTTP-пути
используют корутины; блокирующая библиотека `rabbitmq-c` работает в отдельном
потоке publisher, а не в обработчике веб-запроса. PostgreSQL-клиенту задан
таймаут 5 секунд, Redis-клиенту — 1 секунда.

## Создание и изменение

Для создания и присоединения API генерирует случайный токен из 32 байт,
возвращает его клиенту как 64 hex-символа и сохраняет в БД **SHA-256** токена.
Для хода/завершения сервер получает `X-Player-Token`, хеширует его и ищет
соответствующую сторону в `game_players`. Не доверяется присланный клиентом
номер игрока.

На примере хода:

1. Проверяются UUID, наличие токена и JSON с `from`/`to`.
2. Из PostgreSQL читается актуальная игра, проверяются игрок, состояние и очередь.
3. Игровая логика проверяет допустимость и вычисляет новый `Position`.
4. Один SQL CTE обновляет игру с условием `WHERE version = ...`, записывает
   участок хода и outbox-событие; при победе добавляется `game.finished`.
5. После успешной записи API пытается инвалидировать `game:{id}` в Redis и
   отвечает клиенту. Фоновый поток обрабатывает outbox отдельно.

[Схемы чтения и записи](flows.md) показывают этот путь по компонентам.

Если два запроса пытаются изменить одну версию, проходит только один;
остальной получает `409 Conflict`. При отсутствии обязательного токена —
`401`, при чужом токене — `403`, при неправильном ходе — `422`. Детали
контракта и примеры — в [справочнике API](../development/api.md).

Инвалидация Redis может не выполниться при его отказе: успешная запись БД
не откатывается. Publisher повторно инвалидирует ключ при обработке outbox;
кеш также ограничен TTL. Это снижает, но не исключает временное устаревание.

## Health и журналы

`GET /health/live` проверяет, отвечает ли процесс. `GET /health/ready`
проверяет доступность PostgreSQL и таблицы outbox: если БД недоступна,
возвращается `503`. Redis и RabbitMQ по принятой политике не обязательны
для readiness: чтение может идти из БД, а события могут ожидать в outbox.

API пишет технические сообщения в stdout/stderr, включая `game_id` и
`request_id`; исходные токены не должны попадать в журналы. `X-Request-Id`
принимается, если содержит до 64 буквенно-цифровых символов или дефисов;
иначе создаётся UUID. Полностью единый JSON-формат логов API не заявлен.

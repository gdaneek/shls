# PostgreSQL и модель данных

## Источник истины

PostgreSQL 17 хранит игры, участников, историю участков хода и outbox.
API работает с текущим primary; после переключения этим primary может быть
сервис с именем `postgres-standby`. Определить его можно командой
`infra/postgres/postgres-primary.sh`.

`infra/postgres/schema.sql` содержит один атомарный `DO`-блок, который API
читает при запуске. `CREATE TABLE IF NOT EXISTS` и совместимые изменения
позволяют повторять инициализацию; отдельного инструмента миграций нет.
В контейнере файл находится по пути из `POSTGRES_SCHEMA_FILE`, а исходный
файл остаётся каноническим в репозитории.

## Таблицы

```{graphviz} ../_static/data-model.dot
:alt: Модель данных: games связана с game_players и moves; outbox_events содержит события
```

| Таблица | Основные данные |
|---|---|
| `games` | UUID, статус, строка доски, очередь, победитель, версия, время и контекст незавершённого взятия. |
| `game_players` | Пара `game_id`/`side` и хеш токена; максимум по одной записи на сторону. |
| `moves` | Номер участка, сторона, координаты в виде индексов 0–63, жертва и признак превращения. |
| `outbox_events` | Последовательность, `event_id`, `game_id`, тип, `request_id`, JSON-данные и время. |

Участники и ходы связаны с игрой через внешние ключи. `outbox_events.game_id`
содержит идентификатор игры, но внешним ключом не объявлен. Номер в `moves`
— номер API-участка; продолжение цепочки записывается следующей строкой,
а не одной записью на всю спортивную комбинацию.

Состояния: `waiting` после создания, `active` после присоединения чёрных,
`finished` после победы, сдачи или закрытия ожидающей игры. `winner` может
быть `null`, например при закрытии ожидающей игры. `version` увеличивается
при изменении игры; проверка версии в SQL защищает от конкурентной записи.

## Реплика и тома

`postgres-data` и `postgres-standby-data` — разные именованные тома. Новый
standby первоначально клонируется через `pg_basebackup`; затем получает WAL
по потоковой **асинхронной** репликации. Для неё создан отдельный пользователь
`mini_checkers_repl` с правом replication, а не superuser.

В проекте приложение использует унаследованного владельца/администратора БД;
полное разделение привилегий этого пользователя не заявляется. Сетевые правила
и `pg_hba.conf` ограничивают подключения, но SQL и WAL внутри сегмента не
шифруются TLS в текущем стенде.

Асинхронная реплика может отставать. При аварийном переключении последние
непереданные транзакции могут потеряться. Реплика не заменяет бэкап: ошибка
или удаление, попавшие на primary, также реплицируются. Эти ограничения
рассмотрены в статье [надёжность](reliability.md).

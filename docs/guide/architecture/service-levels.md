# Уровень обслуживания и наблюдаемость

## SLA, SLI и SLO

**SLA (Service Level Agreement)** — соглашение с потребителем об уровне
обслуживания и последствиях его нарушения. Внешний SLA для Mini Checkers
не установлен: нет договорной доступности, времени поддержки и компенсаций.

**SLI (Service Level Indicator)** — измеряемое свойство сервиса:
корректность ответа, задержка, время доставки события.
**SLO (Service Level Objective)** — целевое значение SLI с определёнными
условиями и окном оценки. Ниже заданы внутренние цели проекта.

## Качество чтения и доставки

| SLI | SLO | Граница измерения |
|---|---|---|
| Корректные чтения / все чтения | ≥99% в окне 100 последовательных запросов | Неизменяемая партия; успех — HTTP 200 с ожидаемыми ID, доской, статусом и версией. Таймаут и неверное содержимое считаются ошибкой. |
| p95 задержки корректных чтений | ≤0,5 с в том же окне | HTTP-время внутри API-контейнера; без запуска Docker exec, Nginx и браузера. Неуспешные ответы учитываются отдельно. |
| Своевременно обработанные `game.created` / созданные события | 100% в окне 5 событий, каждое ≤15 с | От начала создания партии до появления записи об обработке в логе worker. |

Условия: один локальный Compose-стек, работающие зависимости и отсутствие
параллельной нагрузки. Полсекунды оставляют запас для интерактивного чтения;
15 секунд — для фонового опроса outbox и переподключения к брокеру.
Эти окна характеризуют отдельные операции; месячный SLO доступности
и сквозной SLO задержки от браузера не заданы.

Своевременная доставка и сохранность — разные свойства. Во время отказа
брокера событие может нарушить цель 15 с, но сохраниться в outbox и быть
доставлено позже. Аналогично readiness API не означает, что очередь уже обработана.

## MTBF и MTTR

**MTBF (Mean Time Between Failures)** — суммарное время штатной работы
компонента, делённое на число незапланированных отказов. Цель — **≥8 ч**:
непрерывная работа в течение рабочего дня. Плановые остановки исключаются.

**MTTR (Mean Time To Recover)** — суммарное время восстановления, делённое
на число отказов. Начало — потеря функции компонента; конец — возврат этой
функции. Для авторестарта процесса признак восстановления — новый запуск
и успешный healthcheck. Для переключения БД — успешная запись на новом primary;
для брокера — возобновление обработки событий.

Средние MTBF/MTTR требуют истории эксплуатации и сейчас не установлены.
Пределы длительности отдельного восстановления:

| Отказ | Целевое время | Основание |
|---|---|---|
| Процесс API, worker или Redis | ≤30 с | Запас на restart policy, сетевые таймауты и healthcheck. |
| Процесс PostgreSQL или RabbitMQ | ≤60 с | Восстановление хранилища и клиентских соединений. |
| PostgreSQL primary с promotion standby | ≤60 с от аварии до новой записи при немедленном действии оператора | Включает promotion и пересоздание API; возврат старого узла выполняется позже. |
| Лидер очереди или узел подключения RabbitMQ | ≤60 с до обработки события при оставшихся 2/3 узлах | Выбор лидера и перебор адресов клиентами. |
| Создание backup и восстановление контрольных данных | ≤300 с для небольшой БД | Логический dump и restore; не восстановление всего хоста. |

## RTO и RPO

**RTO (Recovery Time Objective)** — допустимое время до восстановления
функции, **RPO (Recovery Point Objective)** — допустимая потеря данных,
выраженная временем. Цели переключения выше относятся к доступным репликам
на работающем хосте. Полный простой при ручном promotion также включает
обнаружение отказа и реакцию оператора; предел 60 с их не гарантирует.

У PostgreSQL асинхронная репликация: потенциальная потеря определяется
отставанием WAL на standby. Численный RPO для аварийного переключения не задан;
нулевая потеря подтверждённых транзакций не гарантируется.
При восстановлении из ежедневного backup точка возврата — снимок последнего
успешного dump. При непрерывном выполнении расписания интервал между снимками
около суток; пропуски увеличивают его. Для потери всего хоста RTO не задан.

## Наблюдаемость

| Сигнал | Что означает в проекте | Доступные данные |
|---|---|---|
| Latency | Время корректного чтения и доставки события | HTTP-время запроса; время создания события и его обработки. |
| Traffic | HTTP-запросы и обработанные события за интервал | Access log Nginx; записи worker и `processed_total`, сбрасываемый при рестарте. Повторы отличают по `event_id`. |
| Errors | Транспортные ошибки, HTTP 5xx, неверное состояние при HTTP 200 | Ответ API, журналы SQL/Redis/AMQP. Ожидаемые 4xx отделяются от отказов сервиса. |
| Saturation | Нагрузка CPU/RAM/диска, накопление необработанной работы | Данные Docker и хоста, глубина очереди, число и возраст строк outbox. |

API логирует изменения с `game_id` и `request_id`, publisher — с `event_id`.
Worker пишет JSON с типом, ID, `redelivered` и payload события; в payload
сохраняется `request_id`. Это позволяет связать запрос, публикацию и обработку.
Единого JSON-формата всех сервисов и распределённого tracing нет.

Liveness API подтверждает ответ процесса; readiness — доступность БД/outbox.
Healthcheck worker проверяет свежесть heartbeat (менее 15 с), а не бизнес-SLO.
Логи, healthchecks и точечные измерения доступны; постоянный сбор метрик,
дашборды Prometheus/Grafana и автоматические оповещения не настроены.

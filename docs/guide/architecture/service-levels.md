# Параметры надёжности

Система работает на одном хосте. Значения ниже — цели для
локальной проверки, а не обещание доступности в production.

## MTBF и MTTR

**MTBF** — среднее время работы между незапланированными отказами:
суммарное время штатной работы делится на число таких отказов. Цель для
каждого компонента — **не менее 8 часов**: продолжительность рабочего дня. Плановые остановки и искусственные сбои не учитываются.
Длительного наблюдения не было, поэтому фактический MTBF неизвестен.

**MTTR** — среднее время восстановления после отказа. В контролируемых
опытах время измеряется от остановки процесса до состояния `healthy` и
увеличения счётчика перезапусков. Цель для каждого такого опыта — **не более
30 с** для API, worker и Redis, **60 с** для PostgreSQL и RabbitMQ. Запас
учитывает сетевые таймауты и интервалы healthcheck. Один опыт не является
измерением среднего MTTR. Проверка: `CHECKERS_DISRUPTIVE=1 python3 -B tests/integration/test_failure.py`.

## SLI и SLO

**SLI** — измеряемый показатель качества, **SLO** — цель для него в заданных
условиях. При работающих зависимостях проверяются:

| Показатель | Цель | Проверка |
|---|---|---|
| Корректные ответы на чтение одной тестовой игры | ≥99 из 100 запросов | `python3 -B tests/integration/test_slo.py` |
| p95 времени корректных чтений из API-контейнера | ≤0,5 с в той же выборке | `python3 -B tests/integration/test_slo.py` |
| События `game.created`, обработанные worker | 5 из 5 за ≤15 с от начала создания | `python3 -B tests/integration/test_slo.py` |
| Восстановление после отказа лидера RabbitMQ или узла подключения worker | ≤60 с при двух работающих узлах из трёх | `CHECKERS_DISRUPTIVE=1 python3 -B tests/integration/test_rabbitmq_failover.py` |
| Backup и восстановление контрольных данных | ≤300 с для небольшой тестовой БД | `python3 -B tests/integration/test_backup.py` |

Ограничение p95 выбрано для интерактивной игры; 15 с на событие и 60 с на
восстановление брокера дают запас для переподключений. Пять минут на backup
и restore достаточно для небольшой базы. Это короткие приёмочные
выборки, **не** оценка доступности за месяц и не нагрузочный тест.

Для отказа PostgreSQL отдельно проверяется цель **≤60 с** от аварии primary
до новой записи на standby при немедленном запуске переключения оператором
(`CHECKERS_DISRUPTIVE=1 python3 -B tests/integration/test_postgres_failover.py`). В неё входят promotion и пересоздание
API, но не время реакции оператора и возврат старого узла.

## Результаты проверок

Python-прогон 13.11.2026 после замены shell-сценариев: **100/100** корректных
чтений, p95 **0,001193 с**, **5/5** событий за ≤15 с; backup и restore
контрольных данных — **2,81 с**. Общий `unittest`-прогон: **25 PASS, 11 SKIP**.

Исторические опыты 10.11.2026 с прежними shell-сценариями: переключение
PostgreSQL — **13 с**, обработка после отказа лидера RabbitMQ — **8 с**.
Новые Python-сценарии отказов реально ещё не запускались: эти старые замеры
не подтверждают их прохождение. Все значения — результаты отдельных опытов,
а не долгосрочные средние.

Тесты отказов останавливают компоненты и предназначены для демонстрационного
стенда. Механизмы и их ограничения описаны в разделе [«Надёжность и отказы»](reliability.md).

# События, outbox и worker

## Зачем отдельный worker

Игровой запрос должен менять состояние партии, а обработка уведомления может
происходить позже. Game API и Event Worker — разные процессы и контейнеры;
они взаимодействуют через RabbitMQ. Worker делает намеренно простое действие:
записывает структурированное событие в stdout. Он не получает доступ к
игровым таблицам.

Типы событий: `game.created`, `player.joined`, `move.made`, `game.finished`.
Тело содержит как минимум `event_id`, `game_id`, `type`, `request_id`,
`occurred_at` и объект `data`. Значения `data` зависят от типа события.

## От изменения игры до обработки

```text
HTTP запрос
  → SQL: изменение игры + INSERT outbox_events в одной транзакции
    ├─ обработчик: инвалидация Redis → HTTP-ответ
    └─ publisher: чтение outbox → повторная инвалидация Redis
       → RabbitMQ publish
         ├─ confirm → publisher удаляет строку outbox
         └─ worker получает событие, пишет лог, отправляет ACK
```

Обе ветви начинаются после коммита; HTTP-ответ и асинхронная обработка не
гарантируют определённого порядка относительно друг друга. Confirm подтверждает
приём брокером, а не обработку worker; удаление outbox не ждёт consumer ACK.

Поток publisher читает outbox в порядке `sequence`. В Compose работает один
экземпляр API и один такой publisher; механизм не заявлен как готовый к
одновременной работе нескольких издателей без дополнительной координации.
Если брокер недоступен или подтверждение не получено, строка остаётся в БД и
публикация повторяется. Таймаут AMQP — 5 секунд, задержка повтора publisher —
около 1 секунды.

При сбое после publisher confirm, но до удаления outbox, одно и то же событие
может быть отправлено повторно с прежним `event_id`. Worker логирует его и
не выполняет бизнес-дедупликацию. Это **at-least-once** в описанных условиях,
не exactly-once. Не обещается отсутствие потерь при потере всей машины,
диска, большинства реплик или неподтверждённых транзакций PostgreSQL.

## Очередь и подтверждения

`game.events.quorum` — долговечная quorum-очередь RabbitMQ с тремя репликами.
Для работы требуется большинство 2/3. Когда лидер очереди недоступен,
оставшиеся участники выбирают нового; клиенты перебирают три адреса при
восстановлении соединения. Publisher использует persistent messages и
publisher confirms. Worker отправляет ACK **после** успешной записи лога;
неподтверждённое сообщение может быть доставлено повторно.

Очередь объявлена с `x-delivery-limit=-1`: не применяется стандартное
автоматическое удаление после ограниченного числа повторных доставок. Это
не заменяет отдельную политику dead-letter или контроль размера очереди.
При потере большинства события ждут в outbox; при длительном отказе таблица
может расти. Поведение системы при отказах — в статье [надёжность](reliability.md).

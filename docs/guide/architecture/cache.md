# Redis и cache-aside

## Чтение

Redis хранит сериализованное представление партии под ключом `game:{id}`.
UUID нормализуется к нижнему регистру. При `GET /games/{id}` API:

1. Пробует получить ключ из Redis.
2. При наличии записи актуального формата возвращает её: `X-Cache: HIT`.
3. При промахе читает PostgreSQL, записывает JSON в Redis с TTL и отвечает
   с `X-Cache: MISS`.
4. Если Redis недоступен или чтение завершается ошибкой, обращается к БД и
   обозначает такой режим `X-Cache: BYPASS`.

В Compose TTL задан как 60 секунд (`CACHE_TTL_SECONDS`). Старые записи без
`rules_version: 2` не используются как актуальное состояние. Если запись
нового значения в Redis не удалась, сам запрос к БД может остаться успешным.

## Запись и ограничения

После подтверждённого изменения БД Game API удаляет ключ. Publisher также
пытается удалить его, прежде чем отправлять событие из outbox, в том числе
при повторной обработке после аварии. Если Redis недоступен, это не откатывает
коммит в PostgreSQL.

Одновременный cache miss и запись могут привести к временному устареванию:
инвалидация плюс TTL **не обеспечивают линейной согласованности**. Вкладка
отбрасывает ответ с версией игры ниже уже известной, но это не заменяет
серверную транзакцию. Во время управляемого promotion PostgreSQL скрипт
очищает только ключи `game:*`, потому что кеш может содержать данные, которых
ещё не было на асинхронной реплике.

Redis настроен как одноразовый кеш без дисковой персистентности. Потеря его
данных не должна удалять партии, поскольку источник истины — PostgreSQL.

# Чтение и запись состояния

## Запись: база, кеш, событие

```{graphviz} ../_static/write-flow.dot
:alt: Запись в PostgreSQL и outbox, инвалидация кеша и асинхронная доставка события
```

Для создания, присоединения, хода или завершения API сначала проверяет
входные данные и необходимые права. Изменение игры и вставка события в
`outbox_events` выполняются атомарно в PostgreSQL. Если SQL-запись не
состоялась, кеш и событие не представляют успешную операцию.

После коммита обработчик пытается инвалидировать `game:{id}` в Redis и
возвращает результат HTTP-клиенту. Отдельный поток читает outbox, повторно
инвалидирует ключ и публикует событие в RabbitMQ. Он удаляет строку outbox
после publisher confirm. Worker логирует событие и отправляет ACK.
Публикация асинхронна: HTTP-ответ не ждёт обработки события worker.

При конкурентных ходах SQL проверяет `version`. Два запроса, исходившие из
одной версии, не должны одновременно изменить игру: один получит конфликт.
Подробнее — [Game API](backend.md) и [события](events.md).

## Чтение: cache-aside

```{graphviz} ../_static/read-flow.dot
:alt: Чтение Redis, при промахе или недоступности чтение PostgreSQL
```

`GET /games/{id}` сначала обращается к Redis. На попадании отдаётся кеш;
на промахе состояние читается из PostgreSQL и помещается в Redis с TTL.
Если Redis недоступен, API использует PostgreSQL без него. Заголовок
`X-Cache` показывает `HIT`, `MISS` или `BYPASS`.

PostgreSQL остаётся источником истины. Cache-aside с TTL и инвалидацией
уменьшает устаревание, но не обеспечивает строгой линейной согласованности;
возможна гонка между чтением и записью. Подробности — [Redis и cache-aside](cache.md).

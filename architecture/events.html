События, outbox и worker

Путь события

  1. API фиксирует изменение игры и outbox-событие в одной транзакции.

  2. После коммита обработчик пытается удалить game:{id} из Redis и отвечает клиенту.

  3. Отдельный поток API читает outbox по sequence, повторяет инвалидацию кеша и публикует persistent message через rabbitmq-c.

  4. После publisher confirm удаляет строку outbox. Без confirm строка остаётся для повтора.

  5. Worker получает сообщение, пишет JSON-лог в stdout и лишь затем отправляет ACK.

Confirm подтверждает приём брокером, а не обработку worker. Удаление outbox не ждёт consumer ACK; HTTP-ответ также не ждёт этих действий. Повторная инвалидация нужна при падении API между SQL-коммитом и первым DEL.

Сообщение и очередь

Типы: game.created, player.joined, move.made, game.finished. JSON содержит event_id, game_id, type, request_id, occurred_at, data. Worker записывает тип, ID, payload и признак повторной доставки в stdout. Связь журналов и показателей описана в наблюдаемости.

game.events.quorum — долговечная очередь с тремя репликами, работающая при большинстве 2/3. Клиенты перебирают адреса rabbitmq, rabbitmq-2, rabbitmq-3. Сетевые операции ограничены таймаутом 5 с; publisher повторяет попытку примерно через 1 с, worker — через 2 с после разрыва.

Гарантии и ограничения

  • Падение после confirm, но до удаления outbox, даёт повтор с тем же event_id. Worker не дедуплицирует логи: доставка at-least-once, не exactly-once.

  • x-delivery-limit=-1 отключает удаление по лимиту повторных доставок. Отдельной dead-letter политики нет.

  • При недоступности брокера или потере quorum события копятся в outbox. В стеке один API/publisher; координация нескольких издателей не реализована.

  • Потеря диска/хоста и потеря последних транзакций при асинхронном PostgreSQL failover не устраняются очередью. Сценарии отказов — в надёжности.

Надёжность и резервные копии

Изоляция отказов

Компонент

Поведение при отказе

Frontend / API

По одному экземпляру; restart policy возвращает завершившийся процесс, но на время восстановления вход или API недоступны.

Worker

Перезапускается и переподключается; события ждут в очереди. Игровая запись не зависит от его доступности.

Redis

API читает PostgreSQL; кеш заполняется заново. Потеря кеша увеличивает нагрузку на БД.

PostgreSQL

Том сохраняет данные после рестарта; асинхронный standby позволяет выполнить ручное переключение.

RabbitMQ

Quorum 2/3 сохраняет работу при отказе одного узла; без большинства публикация ждёт в outbox.

restart: unless-stopped реагирует на завершение процесса. Статус unhealthy сам по себе не перезапускает контейнер. Readiness API требует PostgreSQL/outbox, но допускает отказ Redis и RabbitMQ. Холодный запуск Compose ждёт healthy-зависимостей; деградированный режим относится к уже запущенному API.

PostgreSQL: primary и standby

Primary принимает запись, standby получает WAL по асинхронной потоковой репликации. У узлов отдельные тома; их имена не определяют текущие роли. При потере primary запись останавливается до его восстановления или promotion.

Переключение состоит из четырёх действий:

  1. Старый primary остановлен и ограждён от повторного запуска: два writable-узла не должны одновременно принимать изменения.

  2. Standby повышается до primary. Адрес сохраняется в .env, API пересоздаётся с новым подключением.

  3. Ключи game:* в Redis удаляются: кеш мог содержать версии, не дошедшие до standby.

  4. Старый узел архивируется, приводится к истории нового primary через pg_rewind и возвращается как standby.

Эту последовательность реализуют promote-postgres.sh и rejoin-postgres.sh в infra/postgres/. Promotion ручной, с простоем API. Последние непереданные транзакции могут потеряться; автоматического failover и синхронного RPO=0 нет.

RabbitMQ: quorum и переподключение

У очереди game.events.quorum три реплики. При отказе лидера оставшиеся два узла выбирают нового и продолжают обработку подтверждённых сообщений. Узел клиентского подключения и лидер очереди могут быть разными: при разрыве API/worker перебирают три адреса, независимо от выбора лидера.

После возврата узел догоняет реплики. При потере двух узлов большинство недоступно: брокер не подтверждает новые сообщения, API сохраняет события в outbox. После восстановления publisher продолжает доставку. Повторная доставка допустима; подробности — в модели событий.

Политика резервного копирования

Свойство

Реализация

Формат

Полный логический pg_dump -Fc текущего writable-узла.

Расписание

Ежедневно в 02:00 по локальному времени, после установки пользовательского systemd timer. Нужен работающий user manager; Persistent=true догоняет пропуски.

Хранение

backups/ на хосте, вне основного тома БД; каталог 700, архив 600.

Ротация

Удаление архивов старше 7 дней только после успешного нового dump.

Проверка формата

pg_restore --list перед публикацией готового архива.

Restore

Новая БД, одна транзакция, остановка при ошибке; существующая БД не перезаписывается.

Реализация находится в infra/backups/; путь и срок хранения задаются BACKUP_DIR и BACKUP_RETENTION_DAYS. Наличие читаемого архива подтверждает его структуру, но восстановимость данных определяется успешным restore. Физический архив PGDATA перед rejoin — отдельная копия без автоматической ротации.

Цели времени восстановления и допустимой потери данных описаны в параметрах обслуживания.
